이 프로젝트에 Harness 프레임워크를 설치한 직후 **1회 실행**하는 커맨드다.
기존 소스를 분석해 `CLAUDE.md`와 `docs/` 문서의 placeholder를 채운다.

이미 문서가 채워져 있다면 덮어쓰기 전에 사용자에게 확인을 받아라.

---

## A. 스택 판별

아래를 **실제 파일을 읽어서** 확인한다. 추측하지 마라. 확인 불가한 항목은 비워두고 D단계에서 질문한다.

| 항목 | 확인 경로 |
|------|-----------|
| 빌드툴 | `build.gradle` / `build.gradle.kts` / `pom.xml`, `gradlew` · `mvnw` 존재 여부 |
| Java 버전 | `sourceCompatibility`, `java.toolchain`, `<maven.compiler.source>`, `.java-version` |
| Spring Boot 버전 | 빌드 스크립트의 플러그인/부모 POM 버전 |
| 영속성 | 의존성(`spring-boot-starter-data-jpa`, `mybatis-spring-boot-starter`, `jooq`) + `@Entity` / 매퍼 XML 존재 여부 |
| 마이그레이션 | `db/migration/`, `changelog`, Flyway/Liquibase 의존성. 없으면 "DBA 관리 DDL"로 본다 |
| 테스트 스택 | `spring-boot-starter-test`, AssertJ/Mockito/Testcontainers 의존성, `src/test` 실제 테스트 유형 |
| 사내 프레임워크 | 사내 group ID 의존성, 사내 저장소 URL(`repositories` 블록) |
| 패키지 구조 | `src/main/java` 아래 3~4단계 디렉토리 트리 |

멀티모듈이면 **모듈별로** 다를 수 있다. 루트와 각 서브모듈을 모두 확인하고, 다르면 그 사실을 기록하라.

## B. 빌드 커맨드 검증 — 이 단계를 건너뛰지 마라

A에서 판별한 빌드툴로 커맨드 후보를 만든다.

| 빌드툴 | 빌드(AC) | 컴파일(hook) | 테스트 | 실행 |
|--------|----------|--------------|--------|------|
| Gradle | `./gradlew build` | `./gradlew compileJava compileTestJava` | `./gradlew test` | `./gradlew bootRun` |
| Maven | `./mvnw verify` | `./mvnw -q test-compile` | `./mvnw test` | `./mvnw spring-boot:run` |

wrapper에 실행 권한이 없으면(`-rw-r--r--`) `./mvnw`가 `Permission denied`로 죽는다.
이 경우 **`sh ./mvnw ...` 형태로 기록**하라. wrapper 파일 권한을 바꾸지 마라 — 저장소 상태를 건드리는 일이다.

**테스트가 실제로 실행되는지 반드시 확인하라.** 부모 POM이나 빌드 스크립트가 테스트를 끄는 경우가 있다
(예: parent pom의 `<skipTests>true</skipTests>`, Gradle `test { enabled = false }`).
surefire 출력에 `Tests are skipped.`가 뜨거나 `Tests run:` 줄이 아예 없으면 **테스트는 돌지 않은 것이다.**
이때 빌드 성공은 "컴파일 성공"과 같은 뜻이므로, `# 테스트 미실행` 주석을 달고 D단계에서 보고하라.
플러그인 `<configuration>`에 하드코딩된 값은 `-DskipTests=false` 같은 CLI 옵션으로 덮이지 않는다.
빌드 설정을 임의로 고치지 말고, 사용자에게 알리고 결정을 받아라.

**그다음 컴파일 커맨드와 빌드 커맨드를 각각 1회 실행한다.** 둘 다 돌려야 한다.

컴파일이 통과해도 빌드는 실패할 수 있다 — 기존 테스트 실패, checkstyle/spotless, coverage gate 등
컴파일이 건드리지 않는 이유들 때문이다. **레거시 저장소에서는 이쪽이 오히려 흔하다.**

| 컴파일 | 빌드 | 처리 |
|--------|------|------|
| 0 | 0 | 두 커맨드 모두 `## 명령어`에 그대로 기록. 주석 없음 |
| 0 | ≠0 | 컴파일은 정상 기록. **빌드 줄에만 `# 미검증 — 기존 실패 있음`** 을 달고, D단계에서 실패한 테스트/검사 출력을 원문 그대로 보고 |
| ≠0 | — | 두 줄 모두 `# 미검증`. 실패 출력을 원문 그대로 보고 |

`## 명령어` 코드 블록은 실행·빌드·테스트·컴파일 네 줄을 이 순서로 둔다. 줄을 더하거나 빼거나 순서를 바꾸지 마라. 이유: `execute.py`가 둘째 줄(빌드)을 읽어 step 완료를 직접 검증한다.

빌드가 기존 실패로 깨지는 경우, D단계에서 아래 두 가지를 선택지로 제시하고 사용자 결정을 받는다.

1. AC를 좁힌다 — 전체 빌드 대신 대상 테스트만 (예: `./gradlew test --tests '*Order*'`, `build -x test`)
   좁히기로 정해지면 좁힌 커맨드를 1회 실행해 exit 0을 확인한 뒤 `## 명령어`의 빌드 줄에 기록하고 `# 미검증` 표시를 지운다. `# 미검증`이 남아 있으면 `execute.py`가 step을 실행하지 않고 멈춘다.
2. 기존 실패를 먼저 별도 작업으로 해소한 뒤 하네스를 돌린다

이유: `## 명령어` 섹션은 모든 step의 AC와 Stop hook이 참조하는 단일 진실원이다.
여기가 틀리면 모든 step이 3회 재시도 후 실패하는데, 에러가 **설정 문제가 아니라 코드 문제처럼** 보인다.
더 나쁘게는, AC를 통과시키라는 지시를 받은 에이전트가 이번 작업과 무관한 기존 테스트를 고치기 시작한다.

네트워크·인증이 필요한 빌드(사내 아티팩트 저장소)는 오프라인에서 실패한다. 이 경우도 `# 미검증`으로 처리하되, 원인이 네트워크임을 명시하라.

## C. 문서 채우기

| 파일 | 채울 내용 |
|------|-----------|
| `CLAUDE.md` | 기술 스택, `## 명령어`(B단계 결과). 아키텍처 규칙 CRITICAL 항목은 코드에서 실제로 관찰되는 규칙만 적는다 |
| `docs/ADR.md` | ADR-001 · 003 · 004 · 005를 관찰 결과로. **ADR-002는 D단계 확인 전까지 비워둔다** |
| `docs/ARCHITECTURE.md` | 실제 패키지 트리, 레이어 간 의존 방향, 트랜잭션 경계 위치 |
| `docs/API_GUIDE.md` | 기존 컨트롤러에서 관찰된 URI·상태코드·에러 응답·페이징 실태. 문서의 권장안과 다르면 **양쪽을 모두 적고** 어느 쪽을 따를지 D단계에서 묻는다 |
| `docs/GIT.md` | `git log`에서 관찰된 실제 브랜치·커밋 형식 |
| `docs/STACK_PROFILE.md` | 사내 프레임워크 사용 시에만. **미사용이면 파일을 삭제한다** |
| `docs/PRD.md` | 코드에서 알 수 없다. 손대지 말고 사용자에게 작성을 요청한다 |

### 아키텍처 패턴 판정 규칙

`docs/ARCHITECTURE.md`의 A(Layered) / B(Hexagonal) / C(DDD) 중 하나로 **억지로 분류하지 마라.**

- 셋 중 하나에 명확히 맞으면 → 해당 옵션만 남기고 나머지를 삭제한다.
- 어디에도 맞지 않으면 → 옵션 3개를 모두 삭제하고 **실제 패키지 트리를 그대로 적는다.**
  (예: 도메인별 최상위 패키지 아래에 레이어가 들어가는 구조)
- 모듈마다 다르면 → 모듈별로 나눠 적는다.

문서가 코드와 다르면 문서가 틀린 것이다. 코드를 문서에 맞추려 하지 마라.

## D. 보고 및 확인

작업을 끝내면 아래를 사용자에게 보고하고 승인을 받는다.

1. 판별한 스택 표 (근거 파일 경로 포함)
2. 빌드 커맨드 검증 결과 — 성공/실패, 실패 시 출력 원문
3. 아키텍처 패턴 판정 결과와 근거
4. **확인이 필요한 항목** — ADR-002 패턴 확정, API 규약 불일치, PRD 내용, 판별 실패 항목

## 금지사항

- 소스 코드를 수정하지 마라. 이 커맨드는 문서만 건드린다. 이유: 스택 파악과 리팩터링을 섞으면 둘 다 검증할 수 없다.
- 확인하지 못한 값을 그럴듯하게 지어내지 마라. 비워두고 D단계에서 질문한다.
- **빌드 실패를 고치려 들지 마라 — 기존 테스트 실패도 마찬가지다.** 보고 대상이지 작업 대상이 아니다. 이유: 설치 시점에 무관한 코드를 건드리면 이후 step의 실패 원인을 구분할 수 없게 된다.
